01What this repo is

Every Mac and VM here is configured from this one repository. Installed packages, shell config, editor config, macOS settings, Homebrew apps — all of it is declared in files you can read, and applied by running a command.

The idea that makes Nix different from a pile of shell scripts:

You describe the state you want. Nix works out how to get there.

You never run install this or set that. You edit a file that says what should be true, then apply it. Delete the line and the thing goes away. Two machines reading the same files end up the same.

The practical payoff is that a broken change is undoable. Every apply creates a numbered generation, and the previous one is still on disk.

02Five things to know about Nix

You can be productive here without understanding Nix deeply. You do need these five.

The store

Everything Nix installs lives in /nix/store under a path like /nix/store/vaxpw6gg…-bashrc. That hash covers every input that produced it — change an input, get a different path. Store paths are read-only, always.

Profiles are symlink farms

~/.nix-profile/bin/bat is a symlink into the store. “Installing” means building a new profile and repointing one symlink, which is why it's atomic and instant.

Generations

Each apply creates a new generation and keeps the old one. Rollback repoints a symlink rather than reinstalling anything.

Flakes

flake.nix is the entry point; flake.lock pins the exact version of every input. The lock file is what makes a build reproducible, and why you must commit it.

Derivations

A build recipe. nix eval checks the recipe is well-formed; only nix build runs it. This distinction matters more than it looks: evaluation passing does not mean the thing builds.

04How the repo is laid out

flake.nix              entry point; declares hosts and inputs
flake.lock             pinned input versions — always commit it
lib/
  mksystem.nix         builds a darwinConfiguration (system tier)
  mkhome.nix           builds a homeConfiguration (user tier)
hosts/<name>/          per-machine system settings
modules/
  darwin/              macOS system: homebrew.nix, runit.nix, common.nix
  packages/core.nix    system packages (root needs these)
home/
  common.nix           user config shared by every host
  darwin.nix           macOS-only user config
  linux.nix            VM-only user config
  hosts/<name>.nix     per-machine user config
  packages/            user packages
  dotfiles/            37 plain files: bashrc, nvim, git, jj, ghostty…
overlays/              custom package definitions (e.g. d2)

The split that matters: modules/ is the system tier, home/ is the user tier. Everything else follows from that.

05The two-tier dotfile system

This is the genuinely unusual part of the setup. Read it twice.

Dotfiles live once, in home/dotfiles/. They are delivered two different ways depending on the machine.

Live tier · macOS

~/.bashrc is a symlink back into the repo. Edit the file and it's live in the next shell — no rebuild, no command. This is deliberate; it's the whole reason the setup is arranged this way.

Store tier · Linux VMs

The same file is copied into the store and is read-only. The VM has no checkout of this repo, so a symlink would dangle.

The exception: generated files

A few files aren't delivered whole, because part of them differs per machine. Git and jj identity are the examples — andon uses a work email.

For those, Nix generates a small file with the per-host part and layers it over the editable body:

  • ~/.config/git/config — Nix writes the [user] block, then [include]s config-body, which you edit freely
  • ~/.config/jj/conf.d/00-identity.toml — Nix writes it; 50-main.toml is the editable body

The identity is generated; the body is live. Change the body freely. Changing identity means editing Nix and re-applying.

06Which command applies my change

Two commands. Picking the wrong one wastes time but breaks nothing.

make home    # user tier: packages + dotfiles. No sudo. Seconds.
make         # system tier: Homebrew, macOS defaults, launchd. Sudo. Slow.
You changedRun
Body of a managed dotfilenothing — commit it
A package in home/packages/make home
Added a new dotfilemake home
Anything in modules/ or hosts/make
Homebrew appsmake

make home is safe to run whenever you're unsure. It's idempotent and needs no sudo.

07Cookbook

Add a command-line tool

# 1. find the attribute name
nix search nixpkgs ripgrep
# 2. add it to the list in home/packages/workstation.nix
# 3. apply
make home

Change your shell config

$EDITOR /etc/nix-darwin/home/dotfiles/bashrc
# already live in a new shell — nothing to run

Add a Mac app

# add the cask to modules/darwin/homebrew.nix, then
make

Check a change before applying

nix flake check --no-build          # evaluates everything
darwin-rebuild build --flake .#io   # builds, doesn't apply

Undo

home-manager generations            # list, then run the shown path + /activate
sudo darwin-rebuild --rollback      # system tier

08Rules that will bite you

Use jj, never git

This repo is managed with Jujutsu. jj describe -m, jj new, jj log. Always pass -m — jj opens an editor otherwise. jj git push and jj git fetch are fine; those are the interop layer.

Always --no-build on flake check

Bare nix flake check tries to build the Linux VM configurations, which needs a builder that isn't always reachable. It will fail for reasons unrelated to your change.

Never nix profile install

It puts a package in the same profile Home Manager manages, and the next make home fails with a collision. Add it to home/packages/ instead. The profile should stay empty.

sudo needs Touch ID

So make can't run unattended, and can't run over SSH.

Homebrew never uninstalls

cleanup = "none" is set deliberately. Removing a cask from the Nix file stops it being managed; it does not remove it from the machine. Uninstall by hand if you mean it.

09Troubleshooting

No such file or directory for a tool that exists

Stale path cached by your shell after a switch moved things. Run hash -r, or open a new shell.

make home → home-manager: command not found

The CLI comes from the profile it installs, so a first-time or post-failure run has to bootstrap:

nix run home-manager -- switch --flake ".#paul@$(hostname)" -b hm-bak

“Existing file is in the way”

Home Manager won't clobber a file it doesn't manage. -b hm-bak moves it aside as <name>.hm-bak. The make home target already passes this.

brew bundle fails partway

Homebrew runs last in a system switch, so everything else already succeeded — the system is correctly configured and only Homebrew is incomplete. Re-run make; brew bundle is idempotent. A disabled or renamed cask needs fixing in modules/darwin/homebrew.nix.

A build takes 15 minutes instead of 3 seconds

A flake input moved and something is compiling from source — usually jj, which tracks its main branch. Expected after make update, not a fault.

11Your first day

  1. cd /etc/nix-darwin && ls — read flake.nix top to bottom. It's short.
  2. Open home/packages/workstation.nix. That's what's installed for the user.
  3. Add a tool you like, run make home, confirm it's on PATH.
  4. Edit home/dotfiles/bashrc, open a new shell, watch it already be there.
  5. Commit both with jj describe -m "..." then jj new.

If you understand why steps 3 and 4 need different amounts of work, you understand this repo.
